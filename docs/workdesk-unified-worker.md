# BOARD-9 Тред Борды и чат задачи Workdesk — одна лента

Порядок установки на macOS для уполномоченного оператора. Служба отправки не открывает сокет и получает записи из локальной очереди SQLite. Она опрашивает текущий claim через board-role и этим же адаптером вызывает `post_board_thread_message` или `report_task`. На обычном сервере Борды остаётся входящая обработка SSE.

1. Подтвердить два выделенных служебных UID с разными правами и одну закрытую группу для базы. UID автора записи обслуживает только доверенный нативный launcher и запись в очередь. UID отправителя получает board-role и доступ к очереди. Интерактивный UID не входит в группу. Процессы, выполняющие обычные команды агента, не должны получать право записи в эту базу.
2. Установить код и адаптер из согласованного Git-коммита в каталог, контролируемый администратором. Подготовить новый пустой файл очереди SQLite в отдельном каталоге. Владелец каталога и файла — UID автора записи, группа — закрытая группа. Права каталога `0770`, файла `0660`, у обоих процессов `umask 007`. Проверить ACL всех компонентов пути и права на журналы SQLite. Общая база Борды и её копия в очередь не переносятся.
3. В защищённом конфиге указать `workdesk.unified` со штатным executable/argv и объектом `isolation` с числовыми `writerUid`, `senderUid`, `interactiveUid`, `sharedGid`, абсолютным `queuePath` и точным `executor` из текущего claim. Указать штатный `workdeskDialog` binding с задачей, assignment, UUID открытого локального треда и нативным SID. Конфиги автора и отправителя должны совпадать по этому binding. Доступ к board-role имеет только UID отправителя. Адаптер получает bearer через утверждённое защищённое хранилище. Проверить каталог board-role, в том числе `list_board_tasks`, `post_board_thread_message`, `report_task`.
4. В согласованном окне запустить из существующей панели через утверждённый механизм изоляции `bun --no-env-file /абсолютный/путь/src/entrypoints/workdesk-dialog-run.ts <SID> --unified-only`. Эта форма проверяет прежний SID через собственный App Server и открывает только исходящий нативный MCP. Она не запускает дочернюю Борду и не требует FD 3. Обычная форма launcher сохраняет функцию защищённого чтения. Один и тот же SID нельзя одновременно вести через оба launcher. Перед применением оператор должен подтвердить, что изолированный launcher может продолжить ту же историю и что обычный агент или другой процесс не получает его capability, доступ к доверенной очереди или возможность действовать от его UID. Без подтверждённой границы и сохранения нужного штатного пути для входящего диалога запуск не выполнять.
5. Для `/Library/LaunchDaemons` подготовить root-owned plist с `Label=com.mokuteam.board-workdesk-sender`, `UserName` отправителя, `GroupName` закрытой группы, `Umask=7` (целое), `RunAtLoad=true`. В `ProgramArguments` задать абсолютный путь к установленному Bun, `--no-env-file` и абсолютный путь к `src/entrypoints/workdesk-unified-worker.ts`. В `EnvironmentVariables` указать только пути `APPDATA` и `LOCALAPPDATA` по раскладке `src/adapters/paths.ts`. Оператор проверяет plist через `plutil -lint`, устанавливает его `root:wheel` с режимом `0644` и запускает `launchctl bootstrap system /Library/LaunchDaemons/com.mokuteam.board-workdesk-sender.plist`. Состояние показывает `launchctl print system/com.mokuteam.board-workdesk-sender`. Не назначать `KeepAlive` до проверки штатного запуска.
6. Откат отправителя — `launchctl bootout system/com.mokuteam.board-workdesk-sender` и отключение настройки `workdesk.unified` в изолированном экземпляре. Сохранить SQLite и её журналы при незавершённых операциях. Повтор сообщения использует тот же UUID idempotency, неопределённый результат `report_task waiting` сверяется оператором отдельно. Доступ к bearer отзывается уполномоченным Workdesk-оператором. Действующую Борду и её базу этот порядок не переключает. Исходящие сообщения пока не отображаются обратно в обычном треде из этой очереди. Для этого нужен отдельный путь отображения с проверяемым источником результата, без доступа обычного сервера на запись в очередь.
