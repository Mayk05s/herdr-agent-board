# BOARD-9 Тред Борды и чат задачи Workdesk — одна лента

Порядок установки на macOS для уполномоченного оператора. Служба отправки не открывает сокет и получает записи из локальной очереди SQLite. Она опрашивает текущий claim через board-role и этим же адаптером вызывает `post_board_thread_message` или `report_task`. На обычном сервере Борды остаётся входящая обработка SSE.

1. Подтвердить два выделенных служебных UID с разными правами и одну закрытую группу для базы. UID автора записи обслуживает только доверенный нативный launcher и запись в очередь. UID отправителя получает board-role и доступ к очереди. Интерактивный UID не входит в группу. Процессы, выполняющие обычные команды агента, не должны получать право записи в эту базу.
2. Установить код и адаптер из согласованного Git-коммита в каталог, контролируемый администратором. Подготовить новый пустой файл очереди SQLite в отдельном каталоге. Владелец каталога и файла — UID автора записи, группа — закрытая группа. Права каталога `0770`, файла `0660`, у обоих процессов `umask 007`. Проверить ACL всех компонентов пути и права на журналы SQLite. Общая база Борды и её копия в очередь не переносятся.
3. В защищённом конфиге указать `workdesk.unified` со штатным executable/argv и объектом `isolation` с числовыми `writerUid`, `senderUid`, `interactiveUid`, `sharedGid`, абсолютным `queuePath`, точным `executor` из текущего claim, абсолютным `dialogReadPath` и абсолютным `receiptDir`. `dialogReadPath` открывается SQLite в read-only. Он должен вести к действующей базе со штатно сохранёнными зашифрованными ответами и актуальным binding. Предоставлять доступ к каталогу и SQLite/WAL только на чтение через согласованные ACL. `receiptDir` отдельный, принадлежит UID отправителя, режим `0755`, предки защищены от подмены. Файлы квитанций публикуются атомарно с режимом `0444` и содержат только идентификаторы и результат. Указать тот же binding, executor и путь квитанций в конфиге обычной Борды. Указать штатный `workdeskDialog` binding с задачей, assignment, UUID открытого локального треда и нативным SID. Конфиги автора и отправителя должны совпадать по этому binding. Доступ к board-role имеет только UID отправителя. Адаптер получает bearer через утверждённое защищённое хранилище. Проверить каталог board-role, в том числе `list_board_tasks`, `post_board_thread_message`, `report_task`.
4. В согласованном окне запустить из существующей панели через утверждённый механизм изоляции `bun --no-env-file /абсолютный/путь/src/entrypoints/workdesk-dialog-run.ts <SID> --unified-only`. Эта форма проверяет прежний SID через собственный App Server и открывает исходящий MCP и штатный `read_workdesk_dialog`. Она не запускает дочернюю Борду. Оператор подаёт прежний ключ шифрования по FD 3 из штатного защищённого источника. Это сохраняет чтение ранее записанных зашифрованных ответов. Стадирование новых ответов и ACK остаются функцией отдельного действующего доверенного получателя. Такой получатель для нового запуска ещё не подключён. Обычная форма launcher сохраняет функцию защищённого чтения. Один и тот же SID нельзя одновременно вести через оба launcher. Перед применением оператор должен подтвердить, что изолированный launcher может продолжить ту же историю и что обычный агент или другой процесс не получает его capability, доступ к доверенной очереди или возможность действовать от его UID. Без подтверждённой границы и сохранения нужного штатного пути для входящего диалога запуск не выполнять.
5. Для `/Library/LaunchDaemons` подготовить root-owned plist с `Label=com.mokuteam.board-workdesk-sender`, `UserName` отправителя, `GroupName` закрытой группы, `Umask=7` (целое), `RunAtLoad=true`. В `ProgramArguments` задать абсолютный путь к установленному Bun, `--no-env-file` и абсолютный путь к `src/entrypoints/workdesk-unified-worker.ts`. В `EnvironmentVariables` указать только пути `APPDATA` и `LOCALAPPDATA` по раскладке `src/adapters/paths.ts`. Оператор проверяет plist через `plutil -lint`, устанавливает его `root:wheel` с режимом `0644` и запускает `launchctl bootstrap system /Library/LaunchDaemons/com.mokuteam.board-workdesk-sender.plist`. Состояние показывает `launchctl print system/com.mokuteam.board-workdesk-sender`. Не назначать `KeepAlive` до проверки штатного запуска.
6. Откат отправителя — `launchctl bootout system/com.mokuteam.board-workdesk-sender` и отключение настройки `workdesk.unified` в изолированном экземпляре. Сохранить SQLite и её журналы при незавершённых операциях. Повтор сообщения использует тот же UUID idempotency, неопределённый результат `report_task waiting` сверяется оператором отдельно. Доступ к bearer отзывается уполномоченным Workdesk-оператором. Действующую Борду и её базу этот порядок не переключает. В обычном треде отображается только нейтральная квитанция о подтверждённой отправке или конфликте. UUID связывает квитанцию с очередью и предотвращает второй пост. Неопределённый результат вопроса сверяется оператором в Workdesk.

## Свежие ответы владельца и ACK

Сейчас `--unified-only` требует `workdeskDialog.deliver=false`. Режим открывает уже зашифрованные ответы только на чтение. Новый ответ остаётся в Workdesk до подключения защищённого приёмника. Обычная Борда может показать нейтральный сигнал об обновлении.

Действующий `createWorkdeskDialog` открывает обычную БД. `workdeskDialogStore.stage` в одной транзакции этой БД проверяет handoff и binding, сохраняет квитанцию и вызывает `ProtectedDialogSink.stage(tx, target, message)` с тем же `tx`. Поэтому нельзя подключить существующий sink к headless launcher и заменить путь записи на путь исходящей очереди. Разнесение операций без изменения интерфейса лишит ACK проверки устойчивого сохранения, а открытие общей БД на запись расширит границу доступа launcher.

Минимальная дельта для свежих ответов:

1. Оставить сетевую логику и валидаторы `list_owner_events/read_owner_messages/ack_owner_messages` в одном общем цикле. Вынести из него порт хранилища с операциями `cursor/retain/pending/resolve/stage/current/confirm`. Для обычного launcher сохранить действующую реализацию и транзакцию. Для `--unified-only` предоставить отдельную реализацию с закрытым хранилищем входящего диалога. Авторизация чтения и ACK проходит через утверждённый адаптер с правами на эти методы. Наличие исходящего board-role не доказывает, что он их поддерживает.
2. Зафиксировать целевой набор `task_id, assignment_id, thread_id, sid, executor` в защищённом конфиге. Перед чтением и непосредственно перед ACK сверять активный нативный attach, текущий remote claim и revision, открытый локальный тред и handoff через read-only проверку. Устаревшая привязка, остановка App Server, перепоручение или закрытие треда дают отказ. Обычная БД не передаёт тело или указание ACK.
3. Транзакция закрытого хранилища сохраняет курсор discovery, квитанции по `(assignment_id, message_id)` и зашифрованные сообщения. Шифрование переиспользует контекст действующего sink с привязкой к назначению, SID, треду и ID сообщения. При повторе нужно расшифровать уже записанное и подтвердить идентичность тела и метаданных. После commit повторно проверить получателя. ACK относится только к непрерывному проверенному префиксу, уже доступному нативному `read_workdesk_dialog`. При потере ответа ACK выполнить аутентифицированное чтение `delivered_through` и локальную проверку записи перед подтверждением или повтором.
4. Нативный reader читает закрытое хранилище и ранее сохранённый ciphertext по прежнему read-only пути, удаляя дубли по ID. При конфликте записей закрывает выдачу спорной страницы. В обычный тред передаётся только нейтральная квитанция из отдельно проверяемой проекции. Остановка или откат сохраняет закрытое хранилище: подтверждённые сообщения нельзя считать повторно доступными через Workdesk после ACK.

До подключения этого порта и проверки в согласованном окне держать `deliver=false`. Проба включает запись, рестарт до ACK, повтор без дубля, отказ после перепоручения и чтение в том же нативном SID.
