# BOARD-9 Тред Борды и чат задачи Workdesk — одна лента

Порядок установки на macOS для уполномоченного оператора. Служба отправки не открывает сокет и получает записи из локальной очереди SQLite. Она опрашивает текущий claim через board-role и этим же адаптером вызывает `post_board_thread_message` или `report_task`. На обычном сервере Борды остаётся входящая обработка SSE.

1. Подтвердить два выделенных служебных UID с разными правами и одну закрытую группу для базы. UID автора записи обслуживает только доверенный нативный launcher и запись в очередь. UID отправителя получает board-role и доступ к очереди. Интерактивный UID не входит в группу. Процессы, выполняющие обычные команды агента, не должны получать право записи в эту базу.
2. Установить код и адаптер из согласованного Git-коммита в каталог, контролируемый администратором. Подготовить новый пустой файл очереди SQLite в отдельном каталоге. Владелец каталога и файла — UID автора записи, группа — закрытая группа. Права каталога `0770`, файла `0660`, у обоих процессов `umask 007`. Проверить ACL всех компонентов пути и права на журналы SQLite. Общая база Борды и её копия в очередь не переносятся.
3. В защищённом конфиге указать `workdesk.unified` со штатным executable/argv и объектом `isolation` с числовыми `writerUid`, `senderUid`, `interactiveUid`, `sharedGid`, абсолютным `queuePath`, точным `executor` из текущего claim, абсолютным `dialogReadPath` и абсолютным `receiptDir`. `dialogReadPath` открывается SQLite в read-only. Он должен вести к действующей базе со штатно сохранёнными зашифрованными ответами и актуальным binding. Предоставлять доступ к каталогу и SQLite/WAL только на чтение через согласованные ACL. `receiptDir` отдельный, принадлежит UID отправителя, режим `0755`, предки защищены от подмены. Файлы квитанций публикуются атомарно с режимом `0444` и содержат только идентификаторы и результат. Указать тот же binding, executor и путь квитанций в конфиге обычной Борды. Указать штатный `workdeskDialog` binding с задачей, assignment, UUID открытого локального треда и нативным SID. Конфиги автора и отправителя должны совпадать по этому binding. Доступ к board-role имеет только UID отправителя. Адаптер получает bearer через утверждённое защищённое хранилище. Проверить каталог board-role, в том числе `list_board_tasks`, `post_board_thread_message`, `report_task`.
4. В согласованном окне запустить из существующей панели через утверждённый механизм изоляции `bun --no-env-file /абсолютный/путь/src/entrypoints/workdesk-dialog-run.ts <SID> --unified-only`. Эта форма проверяет прежний SID через собственный App Server и открывает исходящий MCP и штатный `read_workdesk_dialog`. Она не запускает дочернюю Борду. Оператор подаёт прежний ключ шифрования по FD 3 из штатного защищённого источника. Это сохраняет чтение ранее записанных зашифрованных ответов. Защищённое получение свежих ответов включается отдельно по условиям ниже. Обычная форма launcher сохраняет функцию защищённого чтения. Один и тот же SID нельзя одновременно вести через оба launcher. Перед применением оператор должен подтвердить, что изолированный launcher может продолжить ту же историю и что обычный агент или другой процесс не получает его capability, доступ к доверенной очереди или возможность действовать от его UID. Без подтверждённой границы и сохранения нужного штатного пути для входящего диалога запуск не выполнять.
5. Для `/Library/LaunchDaemons` подготовить root-owned plist с `Label=com.mokuteam.board-workdesk-sender`, `UserName` отправителя, `GroupName` закрытой группы, `Umask=7` (целое), `RunAtLoad=true`. В `ProgramArguments` задать абсолютный путь к установленному Bun, `--no-env-file` и абсолютный путь к `src/entrypoints/workdesk-unified-worker.ts`. В `EnvironmentVariables` указать только пути `APPDATA` и `LOCALAPPDATA` по раскладке `src/adapters/paths.ts`. Оператор проверяет plist через `plutil -lint`, устанавливает его `root:wheel` с режимом `0644` и запускает `launchctl bootstrap system /Library/LaunchDaemons/com.mokuteam.board-workdesk-sender.plist`. Состояние показывает `launchctl print system/com.mokuteam.board-workdesk-sender`. Не назначать `KeepAlive` до проверки штатного запуска.
6. Откат отправителя — `launchctl bootout system/com.mokuteam.board-workdesk-sender` и отключение настройки `workdesk.unified` в изолированном экземпляре. Сохранить SQLite и её журналы при незавершённых операциях. Повтор сообщения использует тот же UUID idempotency, неопределённый результат `report_task waiting` сверяется оператором отдельно. Доступ к bearer отзывается уполномоченным Workdesk-оператором. Действующую Борду и её базу этот порядок не переключает. В обычном треде отображается только нейтральная квитанция о подтверждённой отправке или конфликте. UUID связывает квитанцию с очередью и предотвращает второй пост. Неопределённый результат вопроса сверяется оператором в Workdesk.

## Свежие ответы владельца и ACK

По умолчанию оставлять `workdeskDialog.deliver=false`. В этом режиме ранее сохранённые ответы и, если указан `inboxPath`, ответы из ранее созданного inbox доступны только на чтение. На старый launcher для этого же SID допускается возвращаться только после остановки headless-приёмника и с сохранением inbox: обычный launcher пока не читает отдельный inbox.

Условия рабочего запуска:

1. Уполномоченный оператор проверяет UID автора записи, ACL и возможность продолжить тот же SID через один App Server. Далее проверяет штатный адаптер входящего диалога (конфигурация `workdeskDialog`, отдельная от обратной записи), его разрешения на `list_board_tasks`, `read_owner_messages`, `ack_owner_messages` и текущий claim. Только после подтверждения ставит `workdesk.unified.isolation.inboxRoleConfirmed=true`. Наличие инструмента в каталоге само по себе не подтверждает роль.
2. В этом же объекте задаёт абсолютный `inboxPath`: отдельный пустой SQLite-файл автора записи с режимом `0600` в отдельном каталоге того же UID с режимом `0700`, без дополнительных ACL и с защищёнными предками. Обычный UID и отправитель не получают доступ. Первая активация создаёт схему. Конфиг и данные очереди отправки не используются для записи входящего тела.
3. В согласованном окне ставит `deliver=true` только для закреплённого назначения и запускает `--unified-only` с прежним ключом по FD 3. Launcher откажет при неподтверждённой роли, неподходящих UID/режимах, отсутствующем каталоге методов, другом native SID либо отсутствии действующей локальной привязки. Штатный локальный binding должен быть уже сохранён обычной Бордой. Базы обычной Борды и исходящей очереди остаются вне транзакции получения.
4. Приёмник проверяет remote claim и нативного получателя, читает валидированную страницу с явным курсором и сохраняет ciphertext и получение одной строкой с первичным ключом `(assignment_id, message_id)`. После commit повторно сверяет remote claim/revision и локальный attach. Workdesk сам перепроверяет текущее назначение при ACK. При рестарте до ACK та же страница перечитывается: сохранённое сообщение расшифровывается для сравнения. Если подтверждение уже применено, `delivered_through` позволяет продвинуть локальный курсор без второго вызова ACK.
5. Проверить в рабочем окне свежий ответ, рестарт между сохранением и ACK, повтор без дубля, отказ после перепоручения и чтение в том же SID. Обычной Борде остаётся её нейтральное уведомление о событии. Доставка тела и ACK происходят только в изолированном launcher. Для отката выключить `deliver`, сохранить SQLite и её журнал, затем возобновить тот же headless launcher в read-only с прежним ключом и `inboxPath`.
